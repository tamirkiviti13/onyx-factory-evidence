THE CODE-GROUNDED FACT THIS PROVES (why "deleted" is the wrong expectation for this lane)
================================================================================================
The OpenClaw INVENTORY detector emits its `*CodingAgentInfo` (the "installed" assertion) ONLY when
`detectAppOrBinary` is satisfied — an OpenClaw app bundle OR the `openclaw` CLI on the user's PATH
(scanner/internal/scanner/agents/openclaw.go:286). `~/.openclaw` is explicitly per-user RESIDUE
(openclaw.go:275-285), NOT the installed signal. So to make the agent genuinely absent from the scan
payload BOTH must go: the CLI (`~/.npm-global/bin/openclaw`) and the dir (`~/.openclaw`).

The scanner only ever reports PRESENCE. When an agent is absent it is communicated by OMISSION — the
scan simply carries no payload for it; there is NO "agent removed" event on the wire. The scanner
ingestion lane (ScannerObjectWorkflow / DesktopAgentCreatorWorkflow) is an ADDITIVE UPSERT keyed on the
asset unique_identifier; it has NO scan-absence -> is_deleted reconciliation and NO scheduled reaper for
scanner desktop agents. (Absence-driven soft-delete exists only in the non-scanner cloud pipelines, e.g.
common/database/repository/agent.py.) The ONLY absence signal for a scanner desktop-agent asset is its
"Last Seen" (`desktop_agent_applications.last_scanned_at`, mirrored on `assets.updated_at`) ceasing to
advance. => A removed OpenClaw asset can only ever go STALE (frozen Last Seen); it is never marked
is_deleted by this lane. That is the honest product behaviour, proven empirically below.
